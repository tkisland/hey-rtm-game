# さくらへのFTP公開手順

公開先は **https://hey.jpn.org/rhythm/**。契約はさくらのレンタルサーバー・スタンダード。ゲームはビルド済み静的ファイルを使用し、Node.jsの常駐やPHP・MySQLの設定は今回の移行には不要です。PHP・MySQLは後続のランキング導入で使用します。

## 1. 初回のサーバー側準備

1. さくらのサーバーコントロールパネルで、`hey.jpn.org`のドキュメントルート（公開フォルダー）を確認します。ドメインごとに異なる場合があるため、無条件に`www/rhythm`と決めないでください。
2. そのドキュメントルートの中に`rhythm`フォルダーを作成します。`https://hey.jpn.org/rhythm/`がこのフォルダーを指す構成にします。
3. 既存の`rhythm`フォルダーがある場合は、変更前の内容をPCへ保存します。ドメイン直下の既存サイト、`.htaccess`、将来のAPIフォルダー・接続設定には触れません。
4. 独自ドメインのHTTPS証明書が有効であることを確認します。既存ドメイン内のディレクトリ追加なので、この移行のためのDNS変更は通常不要です。
5. FTPクライアントを設定します。接続先・アカウントはさくらの案内に従い、FTP接続でTLSが利用できる場合は有効にします。パスワードはチャット・リポジトリへ記載しません。このワークフローにはFTP認証情報の登録は不要です。

## 2. 管理者画面を継続利用する準備

Firebase Authenticationの「設定 → 承認済みドメイン」に **`hey.jpn.org`** を追加します。`https://`・`/rhythm/`は付けません。既存の`tkisland.github.io`は移行確認が済むまで残せます。

Firebaseプロジェクト、`admins`、下書き、公開済み譜面はそのまま使います。MySQLへ移す必要はありません。[管理者設定](google-admin-setup.md)のGitHub変数 **`FIREBASE_WEB_CONFIG`** も継続使用します。値が設定されていないビルドでは収録譜面で遊べますが、管理者ログインは「準備中」になります。既存の設定が登録されているか、GitHubのSettings → Secrets and variables → Actions → Variablesで確認してください。

## 3. アップロード用ZIPを取得する

1. 変更のPRを確認して`main`へマージします。
2. GitHubのActions → **Build site for Sakura FTP** で、そのマージコミットの実行が成功するまで待ちます。手動ビルドはRun workflowでブランチを`main`にします。
3. 成功した実行画面のArtifactsから **`rhythm-site`** をダウンロードします。GitHubへのログインが必要です。
4. ZIPをPCで展開し、直下に`index.html`・`game.html`・`admin.html`・`assets`・`ogp-test-v1.png`があることを確認します。`.vite`はビルドの照合用情報で、含まれていても問題ありません。

PRの実行でも確認用ZIPを作成しますが、通常の本番更新には`main`の成果物を使用します。成果物は30日で期限切れになるため、公開したZIPとコミット番号をPCに保管してください。

**マージやビルドだけでは、さくら上のサイトは更新されません。** 自動FTP送信は行いません。GitHub Pagesへの自動デプロイもこの変更から停止し、以前の公開ファイルはそのまま残します。旧サイトの案内変更は新URLの動作確認後に別途行います。

## 4. FTPで配置する

展開したフォルダーそのものではなく、**中身**を手順1の`rhythm`フォルダーへアップロードします。`rhythm/dist/index.html`や`rhythm/rhythm-site/index.html`にしないでください。

```text
ドメインのドキュメントルート/
└─ rhythm/
   ├─ index.html
   ├─ game.html
   ├─ admin.html
   ├─ assets/          ← JS・CSS・ステージ画像など。フォルダー全体を転送
   ├─ ogp-test-v1.png
   └─ .vite/           ← 照合用情報（任意）
```

更新時は **assetsと画像を先に転送し、HTMLを最後に上書き** します。転送エラーがないことを確認してください。古いタブが参照するハッシュ付きassetsは、移行直後に削除しません。後続のAPIや設定ファイルを消さないよう、「転送元にないファイルを全削除」の同期は使いません。

リポジトリ直下の開発用HTMLや`src`・`node_modules`・`dist-admin`はアップロードしません。開発用HTMLはTypeScriptを直接参照するため、文字だけ表示される原因になります。

## 5. 公開後の確認

1. https://hey.jpn.org/rhythm/ を開き、選曲画面の画像・フォント・両方の曲を確認します。
2. iPhone・Android・PCでゲームスタート、動画、ノーツ音、設定、リザルトからの「もういちど遊ぶ」を確認します。
3. 管理者ログイン、既存の下書きの読み込み、管理者プレビューを確認します。確認のために本番譜面を上書きする必要はありません。
4. https://hey.jpn.org/rhythm/ogp-test-v1.png が直接開けることを確認します。Xなどの共有カードはサービス側のキャッシュに左右されます。
5. 親ディレクトリの`.htaccess`や独自のセキュリティヘッダーがある場合、JS・CSSやYouTube通信を妨げていないか確認します。YouTubeのためにRefererを遮断しないでください（`strict-origin-when-cross-origin`を使用）。

GitHub Pagesとは別オリジンになるため、端末の音量・タイミング補正・初回案内の確認状態は自動では引き継がれません。初回案内から再確認します。Firebase内の譜面はこの影響を受けません。

問題があれば、保管した前回のZIPを同じ順序で上書きして戻します。初回公開なら、さくらへの転送前に保存した元の内容へ戻せます。この操作でFirebaseの譜面データは変わりません。

## 開発時の検証

```sh
npm ci
npm test
npm run build
npm run test:sakura
```

`test:sakura`はビルド済みファイルをローカルの`/rhythm/`以下で配信し、PC・タッチ端末設定で選曲・設定・ゲーム・管理者入口・静的OGPを確認します。YouTubeはテスト用APIで、実GoogleログインやさくらのFTP・実機での動画再生は別途確認します。4185ポートを空けて実行してください。

## 後続の実装

難易度別譜面と管理画面の更新では、[難易度の追加・公開手順](difficulty-setup.md)に従い、FTP転送前にFirestoreのルールを更新します。リザルトのX共有は通常のFTP更新だけで利用でき、XのAPI設定やFirebaseの再設定は不要です。次にPHP＋MySQLの簡易ランキングを追加します。ランキングはログインなし・毎回英数字5〜6文字・同名可・1プレイ1登録とし、曲・難易度・譜面バージョン別に管理します。DBの認証情報は公開フォルダー外へ配置します。今回のZIPにはランキングAPIやDB変更は含めません。
