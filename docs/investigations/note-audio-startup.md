# 冒頭のノーツ音が鳴らない場合の調査

報告：ビスケットケースで冒頭約20秒、ノーツ音が鳴らない。端末はiPhone・Chrome、出力は本体スピーカー。ほかの曲でも最初の数音が鳴らないことがありそう、との追加報告があります。動画の音声が同時に鳴っていたかは未確認。実機固有の原因は未確定です。

譜面に消音指示はなく、ゲームはノーツの成否にかかわらずボタン入力で `TapSound.play()` を呼びます。冒頭20秒だけ止めるタイマーもありません。YouTubeとWeb Audioは別に起動します。

コード上、AudioContextのresumeが長く保留されると、その間に押したノーツ音は再生されません。遅れてまとめて鳴るのを防ぐため、起動完了時に80ms以上古い入力は破棄します。これは以前からの仕様です。一方で、resumeが保留され続ける場合や、解決してもsuspendedのままの場合、通常画面へ失敗が表示されずに進む経路がありました。また、タッチの終了でユーザー操作が認められるブラウザに対し、文書側の起動処理はpointerdownとkeydownだけでした。

## 今回の改善

- pointerup／touchendの信頼されたイベントでも起動を再試行します。
- resumeが解決しても未起動の場合、および再生中の起動待ちが1.5秒続く場合、既存の案内欄に「♫ 音声」での再試行を表示します。動画・ノーツは停止・シークしません。
- 起動を確認できたら準備完了の表示へ戻します。古い入力をまとめて再生することはしません。
- `?sync=1` の診断ログに、`audio.state`、有効状態・音量、音声時計、入力要求数、BufferSourceの開始数、古い入力の破棄数、未起動数、対応ブラウザのaudioSessionの種別を追加します。開始60秒の履歴にも残り、音声状態の遷移はイベントとして保持します。

`started` はWeb Audioへ再生を指示できた数です。スピーカーから実際に聞こえたことや出力遅延は、この値だけでは確認できません。有効状態と音量を確認した上で、入力要求が増えずに無音なら入力経路、要求が増えて開始が0なら起動処理、開始も音声時計も進むなら音量・音声セッション・端末出力などを次に調べます。

端末で再現する場合のURL：`https://tkisland.github.io/hey-rtm-game/game.html?song=biscuit-case&sync=1`。パネルを折りたたんで冒頭をプレイし、無音が起きた直後にログを保存すれば、途中から音が出た場合も前後を比較できます。診断は任意で、外部送信しません。

制御したブラウザテストでは、resumeの保留・タッチ終了でのみ解除できる状態を模擬し、案内と再試行、遅れた音の破棄、音声ログの保存を検証します。これは報告の端末で20秒の無音を再現したことを意味しません。

## iPhone向けの音声セッションの統一

追加調査で、チュートリアルと基準音の調整画面では `navigator.audioSession.type = 'playback'` を指定していた一方、通常ゲームの `TapSound` には同じ設定がないことを確認しました。iPhoneの消音設定や他のメディアと関係する音声セッションの扱いが画面によって異なっていました。この違いと報告された無音の因果関係は、実機では未確認です。

- 全曲共通の `TapSound` で、AudioContextの生成・再開より前にplaybackを要求します。入力時と再生中にも種別を確認します。
- チュートリアルと調整画面も共通ヘルパーを使います。複数の出力が重なる場合は利用中の出力を数え、最後の利用が終わってから元の種別へ戻します。ミュート・終了時も解放します。
- API非対応や設定拒否の場合は従来のWeb Audio処理へ進みます。ノーツ時刻・入力補正・効果音の待ち時間は変更しません。

ブラウザテストでは、playback以外ではAudioContextの再開を拒否する条件を模擬し、ゲームの開始ボタンとYouTube側の開始の両方で、最初の6入力がすぐに再生開始され、実際のWeb Audio出力に非ゼロの音声信号があることを検証しました。ミュート時の復元・再有効化、およびチュートリアル・調整画面も検証しています。これはiPhone実機でのスピーカー出力や20秒の無音の再現・解消を確認したものではありません。
