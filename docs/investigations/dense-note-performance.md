# 連続ノーツ時の負荷調査

連続ノーツで重く感じるという報告に対し、繰り返し処理を確認しました。端末固有のフレーム落ちは未再現で、下記の変更による実機FPS向上は未確認です。

## 確認した繰り返しと変更

- mainの毎フレーム処理で、長オシ状態を全ノーツから1回調べた後、6ボタンの表示のために同じノーツ配列をさらに6回検索していました。1回の走査で取得した保持レーンを、音声とボタン表示に共有します。
- 判定表示では入力ごと／保持中のフレームごとに子要素を検索していました。6レーンのラベルと誤差欄を開始時に保持し、スコアの数値書式も再利用します。
- 毎フレーム生成していた判定帯の投影座標を、画面サイズ・ノーツ表示秒数の変更時だけ計算します。描画座標・判定窓は変更しません。
- 固定の受け取りラインのグラデーションとぼかしを、幅×32px、最大DPR2の小さなキャンバスに保持します。サイズ変更時に作り直します。
- 同時オシの接続線では、まだ表示範囲に届かないグループや判定済みのグループに対する配列生成・ソートを省きます。

ノーツの発光、火花、YouTube、表示秒数、判定仕様は維持します。通常プレイに詳細な音声入力履歴は追加しません。

## 比較と採否

Chromium、390×844、DPR3（描画上限2）、CPUを4倍遅くする条件で、6レーン同時・200BPM相当の密集ノーツを描画し、Canvasの呼び出しと処理時間を確認しました。ノーツごとのぼかしを画像へ置き換える案も試しましたが、画像描画の追加コストがあり、描画処理時間が安定して改善しなかったため採用していません。

固定ラインだけのキャッシュと繰り返し検索の削減に絞っています。合成ベンチマークの変動があるため、FPSや改善率は保証しません。描画時間だけでなくYouTubeのデコードやOS側の負荷も関係するため、実機では診断ログのFPS・最大フレーム間隔と音声入力の記録を合わせて比較します。

ブラウザテストでは、固定描画の再利用・リサイズ、判定帯とノーツ位置の一致、表示秒数と補正、長オシ音・最初の入力、得点集計を確認します。
