# ランキング管理と残りのレビュー対応

## 本番への反映

1. PR #105の結果ID・画像キャッシュを先に反映します。未実施なら既存DBで `002-share-results.sql` を実行してください。
2. 今回の `ranking-setup` 成果物から **`003-ranking-moderation.sql`** を既存DBで実行します。非表示状態と操作履歴の2テーブルを追加するだけです。既存記録・スキーマ番号1・採点ルール7は保持します。繰り返し実行しても記録は消えません。
3. 同じビルドの **`rhythm-site` 全体をFTP更新**します。`moderation.html`・管理用JS/CSS・`api/moderation.php`・`api/moderation-core.php`・`api/rate-limit.php`・更新されたAPI／共有PHPと、隠しファイルの **`.htaccess`** も転送してください。
4. 以前の公開フォルダ `/rhythm/.vite/` があればFTPで削除します。新しい成果物には含めません。Apache側にも古いmanifest.jsonへの拒否設定を置いています。
5. Googleで管理者ログインし、譜面管理画面の「ランキング管理」から操作します。直接 `https://hey.jpn.org/rhythm/moderation.html` を開くこともできます。

追加SQLの前でも既存ランキングは動きますが、管理APIは「追加SQLを実行してください」として操作を拒否します。切り戻し時はサイト一式を以前のビルドへ戻し、追加テーブルを削除しないでください。

## 非表示・復元

曲・難易度を選び、記録に理由（1〜200文字）を入力して「非表示にする」または「復元する」を押します。新しい登録順で50件ずつ表示し、採点ルール・譜面の版も区別できます。理由・操作した管理者のUID・時刻は管理者だけが見られます。履歴は最新20件を画面表示し、DBには全件残します。

非表示の記録は上位一覧と順位計算から除外します。同じプレイに紐づく共有ページ・画像へのサーバーの応答も停止し、登録／共有の再送で解除することはできません。復元すると再び公開します。データを物理削除する機能はありません。同時更新は版番号で検出し、通信失敗後に同じ操作を再送しても履歴を二重登録しません。

結果ID付き共有ページ・画像は再検証するキャッシュ指定に変更し、PNG自体はサーバーのキャッシュを再利用します。既にブラウザやXが取得済みの画像を強制削除することはできません。特にX側のカードキャッシュは別に残ることがあります。

## サーバーでも管理者を確認する

画面のJavaScriptだけで許可しません。PHPはFirebase IDトークンをHTTPSでGoogleのIdentity Toolkitへ照会し、本人・有効期限・プロジェクト・Googleログイン・メール確認・無効化／失効状態を確認します。続いて本人のIDトークンでFirestoreの `admins/{uid}` を読み、`enabled` が真の管理者だけを許可します。署名を検証しないJWTのデコードだけで認証する方式ではありません。

既存のFirebase Web設定を使うため、サービスアカウント鍵・新規プレーヤーログインは不要です。IDトークンはPOSTのJSON本文に含め、URLや操作履歴には保存しません。PHPからIdentity Toolkit API・Firestore APIへのHTTPS接続が必要です。APIキーにサーバーからの接続を拒否する参照元制限を付けている場合は、Firebase側のAPIキー設定も確認してください。

## 回数制限と専用鍵

開始要求は**IPごとに1分180回**が初期値です。学校・携帯回線などの共有IPを考慮して、従来の30回から増やしています。管理APIは別枠で1分60回です。公開フォルダ外の既存config.phpに任意で追加できます。

```php
'start_limit_per_minute' => 180, // 1〜1000
'admin_limit_per_minute' => 60, // 1〜300
```

IPのHMAC鍵にはDBパスワードを使いません。初回利用時に、既存config.phpの隣へ独立した **`rate-limit.key`** を自動作成します。所有者だけが読み書きできる権限0600で保存し、開始要求と管理APIは用途も分けてハッシュ化します。生IPはDBへ保存しません。鍵をGitや公開フォルダへ転送せず、非公開設定と一緒にバックアップしてください。

PHPが `rhythm-private` に書き込める必要があります。作成できない場合はフォルダの所有者・権限を確認します。自動作成を使わない場合は、ローカルで生成した32バイトのランダム値を64桁の16進数として非公開config.phpの `rate_limit_key` に設定できます。キーをチャットへ貼る必要はありません。

## CDN・リバースプロキシ

通常はREMOTE_ADDRを使い、送られてきたX-Forwarded-Forは無視します。CDN等を実際に使う場合だけ、管理しているプロキシの接続元IP／CIDRを非公開config.phpへ明示します。

```php
// 例示用アドレスです。利用中のサービスの実際のプロキシ範囲へ置き換えます。
'trusted_proxies' => ['203.0.113.10/32', '2001:db8::/32'],
```

信頼したプロキシが接続元を正しく付加する構成であることを確認してください。右側から信頼済みプロキシを除いた最初のアドレスを採用し、左側へ挿入した偽装アドレスは使いません。不正なヘッダーは無視します。すべての接続元を無条件に信頼する設定にはしないでください。

## CSP・ID上限・配信ファイル

静的HTMLへContent-Security-Policy-Report-Onlyを付けます。現在はリソースをブロックせず、ブラウザの開発者ツールのコンソールで違反を観測する設定です。外部の報告サービスへ送信しません。YouTube・Firebase・Google Fonts等の許可先を整理してあり、強制するCSPへの切り替えは実際の環境での観測後に行います。共有PHPの既存の強制CSPは保持します。

Apacheのmod_headersが有効なら `.htaccess` から配信します。反映後にHTMLの応答ヘッダーで確認してください。ビルド成果物とApache 2.4の隔離サーバーで設定を検証しますが、本番のサーバーモジュール・許可設定はFTP反映後の確認が必要です。

ノーツIDの上限はブラウザ／PHPとも2,147,483,647です。管理者の読込・保存・公開で超過を検出し、編集で上限を超えるIDを増やす場合もエラーにします。通常のMIDIや既存の収録譜面を変更する必要はありません。

manifestは公開ファイル検証に使った後、成果物から除外します。`ogp-test-v1.png` は旧画像URLとの互換用に現在の版表記なし画像を返すもので、削除しません。

## 本番Firebaseのルール確認（管理者の操作が必要）

この変更でルール本文は変更していません。リポジトリの `firestore.rules` は、下書きへのアクセス・譜面の書き込みをGoogleログイン済みの有効な管理者へ限定し、一般利用者による管理者権限の自己付与も拒否します。エミュレーターで権限拒否を検証しています。

この作業環境には本番ルールを読み取るFirebaseの管理資格情報がないため、**本番に同じルールが適用されていることは未確認**です。以下を管理者のコンソールで確認してください。

1. ゲームで使うFirebaseプロジェクトを開き、Firestore Database →「ルール」を開きます。
2. 公開中の内容をリポジトリの `firestore.rules` と照合します。`admins` の変更拒否、`draftCharts`／`publishedCharts` の管理者限定書き込み、難易度別ドキュメントの条件を確認します。
3. 同じ内容なら追加作業は不要です。異なる場合はプロジェクトと差分を確認してから公開します。CLIを利用する場合は正しいプロジェクトへログインしたうえで `npx firebase-tools deploy --only firestore:rules --project PROJECT_ID` を実行します。

判定の自己申告から人の操作まで証明する仕組みではありません。管理・制限・整合性確認を組み合わせ、ファンサイトとして不自然な記録へ対処できる構成にしています。
